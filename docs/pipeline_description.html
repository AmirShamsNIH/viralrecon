viralrecon

From raw sequencing reads to an annotated, clade-assigned viral genome, for any virus, in one reproducible run.

viralrecon takes Illumina FASTQ files from clinical or environmental samples and a set of reference genomes, and returns per-sample consensus genomes, low-frequency variant calls, contamination profiles, clade assignments and a single report a scientist opens first. It runs on NIH Biowulf and on NIAID's BigSky and Skyline clusters.

Overview

Four questions, one pass

Sequencing a virus straight from a sample answers several questions at once. Answered separately, with scripts rewritten per project, results drift between analysts and cannot be reproduced a year later. viralrecon answers them together, with every tool and parameter recorded alongside the result.

What is in the sample?

Viral, human and bacterial read fractions, so low coverage can be traced to the library rather than blamed on the analysis.

→ Kraken2 · Krona

What does the genome look like?

A consensus sequence per sample and reference, with every low-evidence position masked instead of guessed.

→ consensus FASTA · QUAST

How does it differ from the reference?

Fixed mutations and minority variants down to 2% frequency, annotated with their effect on each protein.

→ FreeBayes · SnpEff

Which known clade is it?

Placement on the published phylogeny for any virus with a Nextclade dataset, with a quality verdict.

→ Nextclade
Overview

The workflow

Every sample is processed against every selected reference. A run can carry several unrelated viruses at once; each result is namespaced sample.reference so they cannot mix. Steps run in this order, scheduled as cluster jobs on SLURM by Snakemake.

  1. 1Reference buildGenome, annotation, indexes
  2. 2Read clean-upRepair, trim, filter
  3. 3CompositionClassify, deplete host
  4. 4AlignmentMap, measure depth
  5. 5Variant callingCall, normalise, annotate
  6. 6ConsensusDepth-masked genome
  7. 7CladeNextclade, when a dataset exists

Stage 8, reporting, gathers all of these across samples. The dashed stage runs only for references that carry a Nextclade dataset.

Stage 1

Reference build

Before any sample is touched, each reference genome is prepared once and registered. A reference can come straight from NCBI by accession, or from a laboratory's own FASTA and annotation, useful when the relevant comparison is a local isolate rather than the historical type strain.

The build downloads the genome and gene annotation, builds the alignment index, the sequence dictionary and a protein-effect database, and records the virus's NCBI taxonomy ID. It also matches the virus to a Nextclade dataset automatically, when one exists. All of this is written into a single registry, genome.json, which accumulates references across projects.

A user-supplied genome and annotation are checked against each other before anything is built. In testing this caught an annotation file in which one gene sat on a sequence name that did not exist in the genome, an error that would otherwise have silently removed that gene from every protein-effect call.

Stage 2

Read clean-up

Repair BBTools reformat 38.87

Raw read pairs are first made structurally valid: junk bases fixed, ambiguous IUPAC codes converted to N, broken pairs dropped, quality values clamped to a sane range.

a single malformed record can crash every tool downstream; repairing first means failures later reflect biology, not file corruption.

Adapters are detected from the read pairs themselves and removed, low-quality bases trimmed, and reads discarded when too short, too low in complexity, or with too many poor-quality bases.

Stage 3

Composition & host depletion

Samples sequenced directly from patients or the environment are mostly not virus. Every read is classified taxonomically against the Kraken2 standard database, producing an interactive Krona chart and a composition table showing the viral, target-virus, human and bacterial fractions.

Human reads, the PhiX sequencing control and bacterial reads are then removed before alignment. This protects patient privacy in downstream files, shortens run time, and prevents host sequence from mapping to conserved regions of the viral genome.

In the validation run, the on-target fraction ranged from 1.5 % to 97.8 % across samples. This single number explains most differences in final coverage, which is why it sits in the summary table beside the genome results.

Stage 4

Alignment

Cleaned reads are aligned to each reference with Bowtie2 in local mode, which tolerates the mismatches expected between a sample and a reference that may be years diverged. Unmapped, secondary and supplementary alignments are filtered out so each read contributes once.

Depth is measured along the whole genome in 200 bp windows and binned at 0, 10, 50 and 100×, the thresholds that decide whether a position can be trusted. Alignment metrics from samtools and Picard feed the project QC report.

A reference that attracts fewer than 1,000 mapped reads is flagged and its downstream steps skipped, so one poor reference in a multi-reference run does not stall the others. Duplicate reads are kept: at the extreme depths typical of viral sequencing, true independent reads share start positions, and removing them would discard real signal.

Stage 5

Variant calling & annotation

A viral sample is rarely a single genome. Within one infection the population carries minority variants: early resistance mutations, co-infections, or the start of a lineage shift. viralrecon calls variants with FreeBayes in pooled-continuous mode, which models the sample as a mixture and reports alleles present in as little as 2 % of reads rather than forcing a diploid-style genotype.

Multi-allelic sites are split into one record per allele and normalised so the same change is always written the same way. Each variant is annotated by SnpEff with its gene, its effect (synonymous, missense, frameshift…) and the protein change in standard notation, for example p.Gln6249His, also given in short form as Q6249H.

Two call sets are kept on purpose: raw, everything the caller saw, and filtered, calls passing quality and depth thresholds. Comparing the two tells a reviewer whether a mutation is genuinely absent from a sample or was present and filtered out.

Stage 6

Consensus genome

Variants are applied to the reference to produce one consensus genome per sample and reference. The critical detail is what happens where the data is thin: every position below 10× depth is written as N.

Without masking, a consensus silently inherits the reference base wherever no reads exist, and a poorly covered sample looks identical to the reference in exactly the regions nobody observed. Masked genomes are honest about what was measured, which matters when they are submitted to public databases or used to build phylogenies.

Each consensus is assessed with QUAST, and the fraction of the genome that reached the depth threshold is reported. Below 80 % coverage the result carries a warning.

Stage 7

Clade assignment

Each consensus genome is placed on the published reference phylogeny with Nextclade, which returns its clade, a list of mutations relative to the dataset's reference, genome coverage, and an overall quality verdict of good, mediocre or bad.

Nextclade is dataset-driven, which is what makes this stage virus-agnostic. Datasets exist for SARS-CoV-2, mpox, RSV, influenza and many more. The dataset is attached to the reference when it is built, so a new virus needs a build step, not a change to the pipeline. A reference without a dataset is skipped rather than described with another virus's nomenclature.

Virus-specific tools that could only ever describe one or two pathogens were deliberately left out, so the pipeline behaves the same way for every virus it is given.

Stage 8

Reporting

Results from every sample are merged per reference and assembled into a single final_report/ directory designed to be read top-down.

One summary table gives one row per sample and reference: read input, composition, mapping, depth, genome coverage, variant count, clade, and a verdict column that reads pass or names exactly which check failed.

Variant matrices show one row per mutation and one column per sample with its frequency, so the question "is this mutation fixed everywhere, or a minority in three samples?" is answered by reading across a line.

Figures and a self-contained IGV report let a reviewer see the read evidence behind each variant in a web browser, with no genome browser installed. Input alignments are downsampled to 200× for this report so it stays around 40 MB per reference instead of gigabytes.

A MultiQC report collects quality metrics from every tool, stage and sample into one page.

Value

Key features

Works for any virus

No step is written for one pathogen. Everything that differs between viruses (genome, annotation, taxonomy ID, Nextclade dataset) is recorded on the reference, so adding a virus is a build command.

Reproducible by construction

Every tool runs from a version-pinned Singularity image, never a cluster module that can change underneath a project. Each run directory keeps the exact code and parameters that produced it.

Minority variants, not just consensus

Population-aware calling down to 2% allele frequency surfaces co-infections and emerging mutations that a consensus-only analysis hides by construction.

Several references in one run

Samples are compared against multiple references at once (for example a historical type strain and a current circulating isolate), with results kept cleanly separate.

Honest genomes

Low-evidence positions are masked rather than filled from the reference, so a genome never claims sequence nobody measured.

A verdict, not just numbers

Each result carries a pass or a named warning (low coverage, too few mapped reads, a failed clade call), so problems are found by reading one column.

Failures stay contained

An annotation that fails for one sample is recorded and reported without discarding the run. The error log stays empty when nothing failed, and lists exactly what did when something does.

Runs on three clusters

The same code runs on NIH Biowulf, NIAID BigSky and NIAID Skyline. Paths, container locations and queue names are resolved per platform from configuration.

Validation

The pipeline was run end to end on the NIAID_1409 project: eight SARS-CoV-2 samples against two references, Wuhan-Hu-1 (NC_045512.2) and a 2023 Omicron isolate (PP115423.1). All 353 jobs completed and all 16 results passed QC. Separately, its variant calls reproduced all seven variants reported by the existing RML analysis of the same data.

Value

Scope

Designed for

  • Illumina short reads, paired-end or single-end, detected automatically
  • Metagenomic or enriched samples from clinical and environmental sources
  • Any virus with a reference genome and annotation
  • Projects comparing samples against one or several references

Not in scope today

  • Long-read platforms such as Oxford Nanopore or PacBio
  • De novo assembly of unknown viruses without a reference
  • Amplicon primer trimming for tiled-PCR protocols
  • Clade assignment for viruses that have no Nextclade dataset
